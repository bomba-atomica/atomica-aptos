# IBE & DKG Test Review Agent Prompt

## Mission

Review the Identity-Based Encryption (IBE) and Distributed Key Generation (DKG) test suite to ensure:

1. **Low-level verification**: Cryptographic confirmations use only foundational crypto libraries
2. **API-level integration tests**: End-to-end tests interact exclusively with high-level DKG/IBE APIs
3. **Fixture generation integrity**: Test fixtures are produced via high-level APIs
4. **Fixture validation integrity**: Fixtures are validated using the identical high-level APIs

## Checklist Item 1: Low-Level Crypto Verification Only

### Goal

When verifying cryptographic correctness, tests should use only foundational crypto primitives (blstrs, ff, group, pairing), NOT the high-level IBE/DKG APIs being tested.

### Valid Patterns

```rust
// ✅ OK: Use pairing() directly to verify DK correctness
let lhs = pairing(dk, &G2Projective::generator().to_affine());
let rhs = pairing(&h_identity.to_affine(), mpk);
assert_eq!(lhs, rhs, "Pairing check failed");

// ✅ OK: Use scalar arithmetic to confirm secret reconstruction
assert_eq!(reconstructed_secret.s, original_secret);

// ✅ OK: Use blstrs serialization for fixture validation
let dk_bytes = dk.to_compressed();
let dk_loaded = G1Affine::from_compressed(&dk_bytes);
```

### Invalid Patterns

```rust
// ❌ WRONG: Using high-level API to verify itself
let verified = verify_decryption_key(&dk, &identity, &mpk);
assert!(verified); // Circular verification

// ❌ WRONG: Re-encrypting to verify ciphertext
let ciphertext_reencrypted = ibe_encrypt(&mpk, &identity, plaintext, rng);
assert_eq!(ciphertext_reencrypted.u, ciphertext.u); // Different RNG = always fails
```

### Review Actions

- [ ] Identify all places where `verify_decryption_key()`, `ibe_encrypt()`, or DKG APIs are used to "verify" results
- [ ] Flag cases where high-level APIs are used for self-verification
- [ ] Confirm low-level alternatives exist (pairing checks, scalar equality, point serialization)

## Checklist Item 2: Integration Tests Use Only High-Level APIs

### Goal

Integration tests should exercise the public API surface (DKG output → IBE encrypt → IBE decrypt) without touching internal implementations.

### Valid Patterns

```rust
// ✅ OK: End-to-end using public APIs only
let transcript = run_dkg_protocol(...);          // DKG API
let shares = extract_shares(&transcript);         // DKG API
let dk = reconstruct_dk(&shares);                 // DKG/IBE API
let ciphertext = ibe_encrypt(&mpk, &identity, msg, rng);  // IBE API
let decrypted = ibe_decrypt(&dk, &ciphertext);    // IBE API
assert_eq!(decrypted, msg);
```

### Invalid Patterns

```rust
// ❌ WRONG: Accessing internal PVSS structures
let internal_share = transcript.raw_shares[0].secret_scalar;
let lagrange = compute_lagrange_manually(...);  // Should use reconstruct()

// ❌ WRONG: Manually computing DK from shares
let dk_g1 = G1Projective::identity();
for (i, share) in shares.iter().enumerate() {
    dk_g1 += share.point.mul(&lagrange[i]);  // Should use high-level reconstruct
}
```

### Review Actions

- [ ] Trace test execution from DKG initialization to IBE decryption
- [ ] Verify no direct access to `DealtSecretKeyShare`, `WeightedTranscript`, or similar internals
- [ ] Confirm reconstruction uses `DealtSecretKey::reconstruct()` or `reconstruct_ibe_dk()`
- [ ] Flag any manual Lagrange interpolation, share aggregation, or crypto primitive calls in integration tests

## Checklist Item 3: Fixtures Generated by High-Level APIs

### Goal

Golden test vectors (fixtures) must be produced using the same high-level APIs that consumers will use.

### Valid Patterns

```rust
// ✅ OK: Using ibe_encrypt() to generate ciphertext fixtures
let ciphertext = ibe_encrypt(&mpk, &identity, plaintext, &mut rng);
json_output.ciphertext_u_g2_hex = g2_to_hex(&ciphertext.u);
json_output.ciphertext_v_hex = hex::encode(&ciphertext.v);

// ✅ OK: Using derive_decryption_key() for DK fixtures
let dk = derive_decryption_key(&secret, &identity);
json_output.reconstructed_dk_g1_hex = g1_to_hex(&dk);

// ✅ OK: Using hash_to_g1() for identity→G1 fixtures
let h_identity = hash_to_g1(&identity);
json_output.h_identity_g1_hex = g1_to_hex(&h_identity.to_affine());
```

### Invalid Patterns

```rust
// ❌ WRONG: Manual point computation bypassing APIs
let dk = G1Projective::generator().mul(&secret);  // Should use derive_decryption_key()
let dk_affine = dk.to_affine();

// ❌ WRONG: Manual ciphertext construction
let u = G2Projective::generator().mul(&r);  // Should use ibe_encrypt()
```

### Review Actions

- [ ] Compare fixture generation code against public API signatures
- [ ] Verify no manual cryptographic operations in fixture generation
- [ ] Confirm generators use the same code paths as production consumers

## Checklist Item 4: Fixtures Verified by High-Level APIs

### Goal

Fixture validation must use high-level APIs to ensure fixtures are consumable by actual users.

### Valid Patterns

```rust
// ✅ OK: Verifying fixtures by decrypting with loaded DK
let ciphertext = load_ciphertext_from_fixture();
let dk = load_dk_from_fixture();
let decrypted = ibe_decrypt(&dk, &ciphertext);
assert_eq!(decrypted, expected_plaintext);

// ✅ OK: Verifying DK correctness via pairing check
assert!(verify_decryption_key(&dk, &identity, &mpk));

// ✅ OK: Verifying DK matches MSK-derived key
let expected_dk = derive_decryption_key(&msk, &identity);
assert_eq!(dk, expected_dk);
```

### Invalid Patterns

```rust
// ❌ WRONG: Re-encryption with different RNG (randomness ensures mismatch)
let reencrypted = ibe_encrypt(&mpk, &identity, plaintext, &mut new_rng);
assert_eq!(reencrypted.u, fixture.u);  // WILL FAIL due to different r

// ❌ WRONG: Manual verification of cryptographic properties
let pairing_result = pairing(&dk, &g2);
let expected = pairing(&h_identity, &mpk);
// This is OK as supplementary check but NOT as primary fixture validation
```

### Review Actions

- [ ] Verify fixture tests load fixtures and consume them via public APIs
- [ ] Confirm no re-encryption or regeneration attempts in validation
- [ ] Check that decryption success is the primary validation mechanism

## Test Categorization Matrix

| Test Type             | Purpose                 | Allowed Operations    | Example                                                   |
| --------------------- | ----------------------- | --------------------- | --------------------------------------------------------- |
| **Unit Test**         | Verify single primitive | Low-level crypto only | `pairing(dk, g2) == pairing(h, mpk)`                      |
| **Integration Test**  | Verify DKG→IBE flow     | High-level APIs only  | `decrypt(reconstruct(dkg_shares), encrypt(mpk, id, msg))` |
| **Fixture Generator** | Create golden vectors   | High-level APIs       | `ibe_encrypt()`, `derive_decryption_key()`                |
| **Fixture Validator** | Verify fixture validity | High-level APIs       | `ibe_decrypt()`, `verify_decryption_key()`                |

## Definitions

- **Low-level crypto library**: `blstrs`, `ff`, `group`, `pairing` - BLS12-381 curve operations
- **High-level API**: `ibe_encrypt()`, `ibe_decrypt()`, `derive_decryption_key()`, `verify_decryption_key()`, `DealtSecretKey::reconstruct()`, `reconstruct_ibe_dk()`
- **Integration test**: Test that chains multiple DKG/IBE operations end-to-end
- **Fixture**: Golden test vector stored in JSON for cross-language verification (Rust ↔ Move)
